# Writing features
How OSes, profiles, variants and features are defined, and what `make validate` checks about them. The coding conventions are in `.claude/CLAUDE.md`; what each feature does is in [Features](features.md).

## OSes, profiles and variants
Each OS is a file in `install/os/`: `os_<os>` returns the `@os` values its features must suit (`platforms`) and the machines it supports (`machines`), and an `os_<os>_<profile>` function for each profile it supports returns that combination's `features` (in the order they run), `optional`, `gui` and `link_paths`. Each profile is a file in `install/profiles/` whose `profile_<name>` returns what holds for it on every OS (`git_fsmonitor`, off for workspaces). Each variant in `install/variants/` only names an OS and profile; `--os` and `--profile` override the variant's, so `--variant steamos --profile minimal` is the SteamOS terminal setup. Features get the OS, the profile, the machine and the enabled features as `feature_<name> <os> <profile> <machine> <enabled>`.

Features for specific hardware (an `@machine` other than `any`, see [Feature docs and requirements](#feature-docs-and-requirements)) live in `install/features/<os>_<machine>/`, e.g. `install/features/steamos_framework16/orei_switch.sh`. `--all` includes them only on their machine; on other machines `--help` lists them under "For other machines", and naming one still runs it, with a warning.

## Feature implementations
A feature can behave differently by OS, machine or GUI through several implementations, which share its name, its `--help` entry and its place in each OS and profile's `features`. Each is a `feature_<name>__<dir>` function in `install/features/<dir>/<name>.sh`, with its own doc comment and tags, where `<dir>` is named after its single `@os`, `@machine` and `@gui` values: the OS, then `_<machine>` and `_<gui>` unless they are `any` (the same rule puts hardware-specific features in `<os>_<machine>/`). `install.sh` runs the one whose tags suit the OS's platforms, the profile's GUI and the machine (`resolve_implementation` in `install/lib/features.sh`), and its `uninstall_feature_<name>__<dir>` and `capture_feature_<name>__<dir>`, if it defines them, for `--uninstall` and `--capture`. When none suits the machine, `--all` leaves the feature out, and naming it runs the one implementation for another machine, with a warning, as for hardware-specific features. `make validate` checks that exactly one implementation suits each OS, profile and machine that any of them suits, and that a feature has either one plain `feature_<name>` or implementations, not both. For example, `desktop_settings` loads dconf settings on GNOME (`arch_gnome/desktop_settings.sh`, `feature_desktop_settings__arch_gnome`) and merges KDE config files on KDE (`linux_kde/desktop_settings.sh`). Implementations are picked by the OS and its platforms as a whole, so a difference between platforms of one OS (Linux and macOS on `portable`) stays inside one implementation, which checks at run time. Use implementations when the steps differ; when only values differ by OS and profile, return them from `os_<os>_<profile>` instead, as `link_paths` is for `link`.

## Feature docs and requirements
Each `feature_<name>` function has a doc comment directly above it: a brief description, a bare `#` line, then tags naming the machines, OS and GUI it works on and the features it requires (`@requires` is optional):

```bash
# Serve a shell in the browser on localhost: download ttyd and install systemd user units that start it on
# demand (see docs/features/webterm.md).
#
# @machine any
# @os linux
# @gui any
# @requires link
feature_webterm() {
```

Each OS returns the `platforms` (`@os` values) and `machines` it targets, and each of its profiles the `gui`. `tests/validation/features.sh` (run by `make validate`) scans `install/features` for `feature_<name>` functions and their implementations and fails if a feature lacks a `feature_description` entry, if a feature function is defined twice, or if an implementation lacks a description, the bare `#` line or the `@machine`, `@os` or `@gui` tag, has text after its tags, or uses a value outside the lists in `install/lib/features.sh`. It also checks that every feature of each OS and profile has exactly one implementation that suits its platforms and GUI on each machine, is for a machine the OS supports, and runs after the features it requires, and that every variant names an OS and profile that go together; `--help` lists each feature's requirements. A feature for specific hardware, and every implementation, must also have a single `@os`, `@machine` and `@gui` and sit in the `install/features/<dir>/` they name (see [Feature implementations](#feature-implementations)), and every other feature at the top of `install/features`. `udev`, `tmpfiles` and `hdmi_audio_fix` hold Framework 16 fixes for any Linux (`linux_framework16/`), `orei_switch` one for SteamOS (`steamos_framework16/`), and `logind` a fix for any Linux laptop (`linux_laptop/`; `laptop` covers `framework16`). On SteamOS, the features that write into `/etc` also name the files SteamOS's default keep list doesn't cover in the keep list `/etc/atomic-update.conf.d/dotfiles.conf`, each in its own subblock, with `keep_across_steamos_updates`, so OS updates keep them. It does nothing where `/etc/atomic-update.conf.d` doesn't exist, so features call it on every OS. The default list keeps system services, sockets and mounts with their enablement links, so `hdmi_audio_fix` has nothing to add, but it keeps nothing in `/etc/systemd/user`.

The tags of every feature are in the [table in Features](features.md#requirements).

## systemd units
Features copy the systemd units they install, never link them, with the helpers in `install/lib/systemd.sh`. `install_system_units` copies units into `/etc/systemd/system`, then reenables and restarts those that changed (`--no-start` skips the restart); `install_user_units` copies them into `/etc/systemd/user`, where every user manager sees them from boot even with an encrypted home, and reenables those that changed for every user. Both only copy units without an `[Install]` section, which another unit starts. `uninstall_system_units` and `uninstall_user_units` undo them. `unit_keep_paths` lists what a feature must add to its keep list subblock: units in `/etc/systemd/user` with their enablement links, and in `/etc/systemd/system` only units that aren't services, sockets or mounts, such as timers. Scripts and binaries that system units or the login screen run go into `/opt/dotfiles/bin` (`root/opt/dotfiles/bin` in the repo), copied with `copy_system_file` (`install/lib/fs.sh`), since the home may still be locked when they run. `/opt/dotfiles` is outside `/etc`, so SteamOS updates keep it without a keep list: SteamOS bind-mounts `/opt` from `/home/.steamos/offload/opt`, which dirlock leaves unencrypted (it only encrypts `/home/deck`), so it is there before login too. `keep_across_steamos_updates` leaves out any path not under `/etc`.

## One-time installs
`install/oti/<name>.sh` defines `oti_<name>` (with `-` as `_`), which runs it, and `oti_config_<name>`, which returns its `description`; it uses the shown-command helpers in `install/lib/exec.sh` (`run_shown`, `run_shown_input`, `run_shown_secret`, `run_shown_to`, `write_shown` and `probe`). `make validate` checks these and that it defines no `uninstall_` functions. See [Installing Arch](one-time-installs/arch-install.md#one-time-installs) for what one does when it runs.
