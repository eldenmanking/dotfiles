# Testing
Checks come in three kinds, each with a make target; `make check` runs all three. Fixtures (`make fixtures`) are a fourth, kept out of `make check` since they need docker or podman and network access.

- **Validation** (`make validate`, `tests/validation/`) enforces the repo's structure, which has to keep holding as files are added, moved or removed: the checkout is a directory named `dotfiles`, the tree in [Layout](layout.md) matches the files tracked by git, `tests/versions.env` pins a SHA-256 for every tool on every platform, every feature is documented and suits the OSes and profiles that use it (see [Writing features](writing-features.md#feature-docs-and-requirements)), every variant names an OS and profile that go together, the README's OS, Profile and Machine table matches the OSes, profiles, machines and variants, every link path exists, naming single files under `root/`, every `uninstall_feature_<x>` and `capture_feature_<x>` names a feature in `DRY_RUN_FEATURES` (both must honor `--dry-run`), and every feature file that copies files into `/etc` calls `keep_across_steamos_updates` (a grep, with exceptions listed in `tests/validation/features.sh`).
- **Lint** (`make lint`, `tests/lint/`) checks code quality: the syntax of every shell, zsh, Python and TOML file, shellcheck (plus a second pass for unused variables that skips `UPPER_CASE` globals, which other files read, and variables an `f_return` returns by bare name; `tests/lib.sh` is checked too), the doc comment of every function (a description and a `Usage:` line, plus a `Returns:` line naming what a function that calls `f_return` returns; see `.claude/CLAUDE.md`), a check that one-time installs (`install/oti`) run their state-changing commands through the shown-command helpers (a line can be exempted with a trailing `# oti-ok: <reason>`), actionlint, no bash 4 features or GNU-only flags (`mapfile`, `declare -A`, `readlink -f`, ...) in `install/`, `install.sh` and `scripts/` (`install/oti` runs on a live ISO and is exempt), and no call of a `_`-prefixed helper from a file other than the one defining it. The shellcheck and actionlint versions are pinned in `tests/versions.env`; `make lint` downloads them into `~/.cache/dotfiles-test` on first use and refuses any download that doesn't match its pinned SHA-256.
- **Tests** (`make test`, `tests/install.sh`) check behavior, so changes don't break what already works. They run `install.sh` in scratch home directories, without touching your own: `--help` and `--dry-run` (plus `--reinstall` and `--uninstall`) for every OS and profile, which must leave the home unchanged; a real `--link --gitconfig` install (plus `--shell` where it writes managed blocks) for every OS and profile that only links under `$HOME`, which a second run must not change; and login and interactive bash and zsh loading the resulting startup files. Set `INSTALL_BASH` to test `install.sh` under another bash, e.g. `INSTALL_BASH=/bin/bash make test` for bash 3.2 on macOS. `tests/webterm_smoke.py` is a separate smoke test for webterm, run by hand (see [Webterm](features/webterm.md#smoke-test)).
- **Fixtures** (`make fixtures`, `tests/fixtures.sh`, needs docker or podman) show and pin exactly what an install does to existing files.
  - Each case in `tests/fixtures/<name>/` has a `case.sh` that names a container image from `tests/images/` (`IMAGE`) and the `install.sh` arguments (`ARGS`), and optionally the paths under `~` whose files `after/` shows in full (`FILES`, by default the shell startup files), the paths outside `~` to compare (`ROOT_FILES`), a command to run after installing (`AFTER_INSTALL`), and a command to run `install.sh` under (`RUN_WITH`, e.g. `dbus-run-session --` for the session bus `dconf load` needs).
  - Next to it, `before/` holds a `home/` tree (for `~`) and a `root/` tree (for `/`), like the repo's own, copied into an otherwise empty home and into `/`.
  - `after/` holds the results once `install.sh` and `AFTER_INSTALL` have run: `manifest`, one line for every entry under `~` (except `~/dotfiles`, but for the `.backup` where `install.sh` moves what it replaces) and under `ROOT_FILES`, with its type, mode, owner, symlink target and the start of its SHA-256; and `home/` and `root/` trees with every symlink the manifest lists, to show the layout the install leaves, and the regular files under `FILES`, `~/dotfiles/.backup` and `ROOT_FILES`, for readable diffs.
  - Each manifest line starts with what the install did to the entry, against a manifest taken just before it (after `before/` is copied in): `new`, `changed` (ending with `(was ...)` and what it was), `kept` (there before and untouched, like the image's own files), or `removed`.
  - Paths and symlink targets under `~` start with `~`, so a manifest doesn't depend on the image's user.
  - Each git clone (zsh plugins, tmux plugins, tools repos) is one line with its remote, followed by its untracked and changed files, since its contents follow upstream; for the same reason the files the `claude` feature builds from the tools repos are listed without a hash.
  - A symlink that doesn't resolve fails the case, as does a `FILES` path inside a symlinked directory (name the symlink instead).
  - Each case runs in a fresh container from a copy of the checkout, and runs `install.sh` again at the end, which must change nothing anywhere under `~` or `ROOT_FILES`: the install is idempotent, and `AFTER_INSTALL` didn't undo any of it.
  - After changing what an install writes, run `tests/fixtures.sh --update [name...]` to rewrite `after/`, and review the change with `git diff`.
  - SteamOS has no container image, so `tests/images/steamos` stands in for it: the same Arch image (SteamOS is built on Arch) with KDE's kconfig tools for `--desktop_settings`, stand-ins for `udevadm`, `systemd-tmpfiles` and the parts of `systemctl` that need a running systemd, and a mock `steamos-update`. Like a real SteamOS update since 3.6, the mock moves every change to `/etc` that no keep list names into `/etc/previous` and restores the original, and it drops files added to `/usr`; its default keep list is reconstructed from a deck's (`tests/images/steamos/atomic-update-keep.conf`), and like SteamOS's its entries are globs. The `steamos-update` case runs it after installing the Framework 16 fixes (`udev`, `tmpfiles`, `hdmi_audio_fix`, `orei_switch`) and `gamescope_screenshot`, so it fails if an update would wipe anything `install.sh` put in `/etc`, while its `before/root/etc/dummy.conf` shows an unlisted file being wiped. The `steamos-update` case installs `light_sleep` too, and the `steamos-uninstall` case runs `--uninstall` twice and then `--reinstall` for the features that can be undone there, checking that their files are gone in between.
  - Both images have neovim, starship and tmux installed so the features don't download them, so fixtures only need GitHub (zsh plugins, tpm, tools repos). Features that need a real desktop (pacman, systemd) or a download are left out of the cases.

zsh and python3 checks are skipped with a warning when those are missing, except in CI. CI (`.github/workflows/`) caches `~/.cache/dotfiles-test` (the pinned tools and the fixtures' downloads), gives every job a timeout, and runs `make validate`, `make lint` and `make fixtures` on Ubuntu (and then points the `install` branch at the commit, see [Installation](installation.md#installing-on-a-fresh-machine)), and `make test` on Arch Linux (in a container whose packages are pinned to an Arch Linux Archive snapshot), Ubuntu and macOS. The macOS job is skipped when no file it tests changed (a `changes` job decides, since macOS minutes cost more), and a skipped job doesn't fail the workflow, so the `install` branch moves only to commits that passed everything that ran, macOS included. Actions are pinned to commit SHAs and kept current by Dependabot; container images, runner labels and `tests/versions.env` are bumped by hand.
