# Test VMs
Two optional SteamOS features make VMs for testing: one to try Arch installs in, one running SteamOS itself. The `test-in-steamos-vm` and `debug-steamos-vm` skills in `.claude/skills` cover working with the SteamOS one.

## Arch install test VM
The optional `--steamos_arch_vm` feature (on the `steamos` desktop profile; `--all` skips it) defines a GNOME Boxes VM named `arch-install` for trying out Arch installs, with two disks:

- The install medium: the latest Arch ISO itself (`~/Downloads/archlinux-x86_64.iso`, downloaded and checked against the mirror's `sha256sums.txt` if missing; delete it to get a newer one). The ISO is a hybrid image, made to be written to a USB stick as is, so the VM attaches it directly as a read-only removable USB disk, first in the boot order. Nothing in the VM can change it.
- `arch-install-target.qcow2` in Boxes' image directory (`~/.var/app/org.gnome.Boxes/data/gnome-boxes/images`), a blank thin-provisioned 40G disk on virtio (`/dev/vda` in the guest) to install onto.

The VM is UEFI (OVMF) with Secure Boot off, since the Arch ISO isn't signed, with 8 vCPUs and 6 GiB of RAM. The disks have the serials `ARCHMEDIUM` and `ARCHTARGET`, so `/dev/disk/by-id` tells them apart. The feature runs `virsh` and `qemu-img` from inside the Boxes Flatpak, so the domain XML (`arch_vm_domain_xml` in `install/features/steamos_arch_vm.sh`) is written under the Flatpak's cache directory, since its sandbox can't see `/tmp`. Each step is skipped when its result exists. `--uninstall` removes the VM, its UEFI variables and the target disk after asking, and keeps the ISO, so `--reinstall` resets the VM to a blank target without downloading anything. The sizes, memory and vCPUs are the `ARCH_VM_*` constants at the top of the file.

## SteamOS test VM
The optional `--steamos_vm` feature (on the `steamos` desktop profile; `--all` skips it) installs SteamOS into a VM named `steamos`, for trying out dotfiles and SteamOS changes without touching the machine; `steamos-vm` (linked into `~/.local/bin`) starts and stops it. It runs under the virt-manager Flatpak's session libvirt with the Flatpak's QEMU extension, which the feature installs: GNOME Boxes' bundled QEMU is too old for DRM native context, which gives the guest the host's real AMD driver (RADV and radeonsi), so Game Mode's gamescope gets Vulkan. Its code is in `install/lib/steamos_vm.sh`, shared by the feature and the script.

**Install.** The feature decompresses the newest `~/Downloads/steamdeck-*repair*.img.bz2` (Valve's recovery image, downloaded if there is none) to `recovery.img` in `~/.var/app/org.virt_manager.virt-manager/data/steamos-vm`, and copies its kernel and initramfs out of its root partition with `btrfs restore`, which needs no root. It then boots the image once as a transient domain, `steamos-install`, straight into that kernel: the image's GRUB draws only on screen, with no timeout to interrupt, so booting the kernel directly is what gives it a serial console and lets it run a command. The kernel arguments are GRUB's, plus `steamos.efi=PARTUUID=<efi-A>` (which GRUB's `steamenv` module adds) and `systemd.run=`, which runs a setup script from a small raw disk and powers off. The script runs Valve's `repair_device.sh all`, which wipes `/dev/nvme0n1` and installs SteamOS (so the VM's disk is NVMe, as on a Steam Deck), then writes into `/etc` of both A/B slots (SteamOS boots B first, and falls back to A after boots that never reach the login screen):

- a serial console login on ttyS0 (`steamos-vm console`);
- `steamos-vm-agent.service`, which answers `ping`, runs `poweroff` or `reboot`, and runs scripts as root (`exec`, for `steamos-vm run` and `sync`) sent over a virtio-serial port. `virsh shutdown` presses the ACPI power button, which Game Mode treats as suspend;
- a `systemd-suspend.service` drop-in that keeps suspend from reaching the kernel. After a guest suspend, S3 or s2idle alike, the virtio-gpu native context loses its host-side state: processes using the GPU hang in the kernel (uninterruptibly, so a reboot waits on them for minutes) and the serial console can die. The drop-in sorts after `light_sleep`'s, so it wins in the VM: on external power (the fake charger below) with `light_sleep` installed, it runs `light-sleep`, which then takes a light sleep (see [light-sleep.md](../light-sleep.md)) and never suspends, so a suspend from Steam or `systemctl suspend` goes the real way through logind; anything else is a no-op, where Steam's idle suspend still runs the sleep hooks (e.g. `orei-switch`) and "wakes" at once;
- `steamos-vm-power.service`, which loads `test_power`, the kernel's fake charger (`test_ac`, a `Mains` supply like the Framework's `ACAD`) and battery, so what depends on the power source can be tested; `steamos-vm power ac|battery` switches it;
- `steamos-vm-wifi.service`, which loads `mac80211_hwsim` for a virtual Wi-Fi radio. When Steam starts without a Wi-Fi device, it sets the Wi-Fi backend through steamos-manager, which stops NetworkManager, fails to create `wlan0` with `iw` (there is no `phy0`), and returns without starting NetworkManager again, leaving the VM offline. With the radio, Steam doesn't switch at all.

Units, their links and `.service` drop-ins in `/etc` survive SteamOS updates. The install takes about a minute and logs to `install.log` in the Flatpak's cache directory (`~/.var/app/org.virt_manager.virt-manager/cache/steamos-vm`); the disk is kept only when the script's done marker shows up. The user `deck` has no password until you set one with `passwd` in the VM. The feature also saves virt-manager's `qemu:///session` connection, without which it says "Could not detect a default hypervisor".

**The VM.** UEFI without Secure Boot, 8 vCPUs, 6 GiB of RAM in shared `memfd` memory (which virtio-gpu's blob resources need), the 64G thin qcow2 disk `disk.qcow2` on NVMe, user networking, a TPM 2.0 (`swtpm`, from the Flatpak's QEMU extension, with its state in `tpm` next to the disk, so it survives the redefinitions below; `--uninstall` removes it), and virtio-gpu with `blob`, `drm_native_context` and 4 GiB `hostmem`, which the XML can only set in a `<qemu:override>` block. It keeps QEMU's own DMI identity, so it is a `generic` machine to `--infer`: with the Framework's, `framework_tool` (`orei_switch`) polls for an embedded controller the VM doesn't have. Install the framework16 features into it with `--machine framework16`; their services find no hardware and stop. The guest's GPU work runs on whichever amdgpu render node libdrm finds first (virglrenderer opens its device with `drmOpenWithType("amdgpu")`, which tries `renderD128` upward; QEMU's `rendernode` only picks the GPU SPICE draws with). With the eGPU connected at boot that is the eGPU, so `steamos-vm start` points SPICE at the same node, redefining the VM when it changed, rather than have every frame cross between GPUs.

**Compared with the Framework 16.** What the VM does to behave like the laptop, and where it still differs, so a test result can be read for what it covers:

- **Matches:**
  - The GPU stack: DRM native context gives the guest the host's real AMD driver, so gamescope, Steam and Plasma run on RADV and radeonsi, as on the laptop.
  - Storage: the disk is NVMe, and Valve's own `repair_device.sh` lays out the A/B slots and `/var` overlays, so `/etc` keep lists and slot fallback behave as on hardware.
  - Network: a virtual Wi-Fi radio (`steamos-vm-wifi.service`), so Steam's Wi-Fi backend switch doesn't take NetworkManager down.
  - Power source: a fake charger (`steamos-vm-power.service`, `test_power`): `test_ac` is a `Mains` supply like the laptop's `ACAD`, switched with `steamos-vm power ac|battery`.
  - Sleep: a suspend goes through logind and `systemd-suspend.service` as on the laptop, and on AC with `light_sleep` installed it takes a real light sleep. Only the kernel's suspend itself is blocked (see the drop-in above).
  - SSH: sshd and logind make an SSH login its own session, as on the laptop, though only from inside the VM (below).
  - TPM: a TPM 2.0 at `/dev/tpmrm0`, as the laptop's firmware TPM, so what seals state to it (e.g. `tailscaled`) behaves the same.
  - SteamOS version: the VM installs from Valve's recovery image, which can be a release behind; `steamos-vm run --root steamos-update`, then `steamos-vm restart`, brings it to the current one on its branch (stable, `rel`, as on the laptop). Everything the setup script put in `/etc` is on SteamOS's default keep list, so it survives the update.
- **Differs:**
  - Hardware: the VM is a `generic` machine with no embedded controller, PD controllers, eGPU on PCIe root port `00:01.5`, lid switch, Bluetooth or real Wi-Fi. The Framework 16 features install with `--machine framework16`, then find no hardware: `framework_tool`, `orei-switch`, `hdmi-audio-fix` and `light-sleep`'s eGPU path can't be checked here.
  - Sleep states: the guest never reaches s2idle or hardware sleep (S0i3), the state that drops the eGPU's link.
  - Network: user networking can't be reached from the host or the LAN, so SSH and webterm are tested from inside the VM (`ssh localhost`, `curl 127.0.0.1:7681`), and Tailscale SSH needs the VM logged in to a tailnet.
  - Desktop Mode: it ran Plasma on X11 (`plasma-kwin_x11.service`), so `light-sleep`'s `kscreen-doctor` step, which only runs with `kwin_wayland`, is skipped there.
  - Display and input: one virtual 1280x800 display, and QEMU's USB keyboard and tablet. Its keyboard has a `/dev/input/by-id/*-event-kbd` link like a USB keyboard, so `light-sleep` wakes on `steamos-vm key`.

**`steamos-vm`.** `start` (the default) starts the VM and waits for its agent; on a running VM it waits for the agent, and force-restarts the VM when it doesn't answer within 2 minutes. It power cycles a suspended VM (one installed before the suspend drop-in), resumes a paused one, retries while libvirt still holds the last run's serial log, then opens its window in virt-manager (`--no-view` skips that). `stop` asks the agent to power off and forces the VM off when it doesn't answer or stop within a minute (`--force` at once). `restart` is a full power cycle. `status` prints the state, whether the agent answers and the render node; `console` attaches to the serial console. `sync [CHECKOUT]` copies a checkout (default `~/dotfiles`) as it is, uncommitted and untracked files included, into the VM's `~/dotfiles` on the same branch name, in a few seconds: it commits the working tree from a temporary index (the checkout's own index, stash and refs are untouched) and sends it as a git bundle over the agent's channel, so the VM needs no network; changes made in the VM's copy are overwritten. `screenshot [FILE]` saves a PNG of Game Mode, which gamescope takes inside the VM (QEMU can't: with GPU acceleration the picture is GPU buffers it never reads back), `key KEY...` presses keys in the VM (`virsh send-key` names, e.g. `KEY_ENTER`), and `power [ac|battery]` plugs in or unplugs its fake charger, or prints which it is on. `run [--root] COMMAND` runs a command in the VM as `deck` (or root) and prints its output, e.g. `steamos-vm run 'cd ~/dotfiles && ./install.sh --variant steamos --link'`; it has no terminal, so features that ask for a `sudo` password need `console`. The agent client is a few lines of host `python3`, which talks to QEMU's socket directly. `--uninstall` stops and removes the VM, its UEFI variables and its disk after asking, and keeps virt-manager and `recovery.img`, so `--reinstall` installs a fresh SteamOS in about a minute; delete `recovery.img` to use a newer image.
